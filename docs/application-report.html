01 Overview

Name: Alameen Distributor Tracker

Purpose: A read-only web dashboard that visualizes the GPS routes, customer visits, and behavioral patterns of distributors (salesmen) working with the Alameen Accounting & Distribution system.

Deployment: Runs on a Windows Server alongside the Alameen application (which runs on IIS). The tracker runs on Apache (XAMPP) on port 8081, coexisting peacefully with the accounting system on port 80.

Access: Local (http://127.0.0.1:8081/alameengeo/public/) and remote (via Cloudflare Tunnel).

Languages: Arabic (RTL, default) + English (LTR).

Theme: Dark (default) + Light, with shared preference across pages.

ℹ️
Core principle: The application is strictly read-only against the production database. Every query is a SELECT. No tables are created, altered, or dropped. No rows are inserted, updated, or deleted.

03 Page-by-Page Description

3.1 — index.php (Main Route Viewer)

The most complex page. Combines the route map, playback animation, analytics, and controls.

Topbar (fixed, safe-area aware)

  • 🚚 Logo + app title
  • 📊 Link to compare.php (multi-distributor comparison)
  • 🖨️ Button to open report.php (route report) — opens in new tab with current filters
  • ⚠️ Button to open report-anomalies.php — visible only when anomalies are detected
  • 🔗 Button to copy shareable URL to clipboard (URL encodes all filters)
  • ☀️ / 🌙 Theme toggle (dark/light)
  • 🌐 Language toggle (AR/EN)

Sidebar panels (top to bottom)

1. Coverage banner — system-wide status. Shows total GPS points, working/total distributors, date range of all data, and a warning if no new GPS has arrived in >14 days.

2. Filter form:

  • Distributor dropdown (all 10 from Distributor000)
  • From / To dates (native picker opens on click anywhere in input)
  • Toggle checkboxes: Route, Visits, Heat map, Coverage, Anomalies
  • Load button (also triggered by Enter in the form)
  • Reset button (clears everything except language preference)

3. Playback panel (appears after a route loads):

  • Play/Pause button
  • Slider to scrub through the route
  • Live clock (HH:MM)
  • Progress counter (X / Y)
  • Speed selector (0.5× / 1× / 2× / 4× / 8×)
  • "Reveal visits as time advances" toggle

4. Stats panel: GPS points, distance (km), days, visits, visits on map, customer GPS count. Warnings appear for empty ranges, thinned routes, and missing coordinates.

5. Days table (clickable):

  • One row per day with a color swatch, date, point count, km, and visit count
  • Click a row → map zooms to that day's bounds
  • Toast shows the day's full summary

6. Anomaly panel (appears when toggle is on):

  • 🔄 Rescan button
  • One row per anomaly with type icon, date/time, duration, nearest customer
  • Click a row → map zooms + crosshair + popup

7. Visits panel (always present, has search):

  • Live search box filtering by customer name, time, trip, state, source
  • Count shows filtered / total when a filter is active
  • Each row shows customer name + time + (approx) or (no GPS) tag
  • Click → zoom + crosshair + popup, or open customer.php if no GPS

Map layers (bottom to top)

  • OSM base tiles
  • Route polylines — one color per calendar day so multi-day ranges don't cross-cut
  • Start marker (green) and End marker (red) for the full range
  • Heat layer (optional, log-scale colored)
  • Coverage canvas layer (optional, grid cells)
  • Visit markers — clustered when zoomed out, individual when zoomed in (purple = stored customer GPS, orange = derived from nearest route point)
  • Anomaly markers (red ? = unknown stop, amber ⏸ = long idle, purple ▶ = far start)
  • Playback vehicle (🚚 pulsing amber circle)
  • Selection crosshair (red pulsing ring + 4 arms)

Smart behaviors

  • Decimation: if a range has >5,000 points, every Nth point is sent to keep the map smooth. Distance and stats are still computed on the full dataset server-side.
  • Persistent state: distributor, dates, and toggles are saved to localStorage and restored on return. If a valid state exists, the app auto-loads.
  • URL state: all filters are reflected in the URL. The 🔗 button copies it.
  • Day-boundary safety: distance uses SQL LAG partitioned per day, so overnight gaps between dates never get counted.
  • (0,0) rejection: any coordinate that resolves to exactly zero latitude AND zero longitude is filtered out.

3.2 — customers.php (All Customers Map)

Purpose: Show every customer with a usable location on one map.

How it works: The API derives coordinates from the customer's most recent visit and finds the nearest route GPS ping within ±15 minutes. This yields 185 customers even though the database has zero stored customer GPS.

Layout

  • Sidebar with distributor filter, search input, and count display
  • Map with clustered markers (blue dots; clusters turn amber >20, red >100)
  • Click a marker → popup with name, last visit time, visit count, distributor, and "View details →" link to customer.php
  • Click a sidebar item → map zooms + red crosshair + popup opens

Caching: The API caches to public/cache/customers-map.json for 1 hour. 🔄 button forces refresh.

3.3 — customer.php (Single Customer Details)

Purpose: Full details of one customer, including visit history.

Intentionally light-themed — this page is meant for reading and printing, not for map work.

Header

Back button, customer name + number, language toggle.

Panels

  • Financial Summary: Debit, Credit, Balance (= Debit − Credit, color-coded red/green/gray), MaxDebit, Warn threshold
  • Contact Information: Phone1, Phone2, Mobile, FAX (all clickable tel: links), Email (mailto:)
  • Distribution Settings: Force visit start with barcode, Force visit end with barcode — each shown as a green "Enabled", grey "Disabled", or dim "N/A" badge depending on the source table
  • Visit History: Last 50 visits with trip number, date, start time, finish time, computed duration, distributor name, and state badge
  • Notes: Free-text with preserved line breaks

Defensive schema detection: Every column is checked against INFORMATION_SCHEMA.COLUMNS before being queried. Missing columns show — instead of crashing.

Responsive: 2-column grid on desktop, single column on phone. Visit table becomes stacked cards under 560px.

3.4 — compare.php (Multi-Distributor Comparison)

Purpose: Overlay routes from multiple distributors on one map for strategic comparison.

Layout

  • Sidebar: date range, distributor checkbox list (with color swatches), All / Clear buttons, Load button, Summary panel
  • Map: one polyline per distributor in a distinct color, start/end markers per distributor

Each distributor gets a fixed color from a 12-color palette, so re-selecting them produces the same color every time.

Summary cards below the list show per-distributor points, km, and days. Click a card → map zooms to that distributor's route.

3.5 — report.php (Printable Route Report)

Purpose: A clean A4 print/PDF report of a distributor's route over a date range.

Server-side PHP header renders the distributor name, dates, and generation timestamp.

JavaScript fetches api/route.php and api/visits.php and renders:

  • 4 stat cards (GPS points, distance, days, visits)
  • Per-day breakdown table (date, points, km, visits)
  • Full visit log (time, customer, trip, state)

Print button (fixed top-right) triggers the browser print dialog. Print CSS hides the toolbar, tightens spacing, and prevents section splits across pages.

Arabic RTL fully supported — the entire report flips.

3.6 — report-anomalies.php (Printable Anomaly Report)

Purpose: A formal, printable report of all anomalies detected in a period.

Content

  • 4 stat cards (total, unknown stops, long idles, far starts) with colored top borders
  • Amber warning banner explaining the report's purpose (investigation aid, not a verdict)
  • One section per anomaly type, each with a count pill
  • Row format: date, time range, duration, nearest customer, distance, coordinates

Sections appear conditionally — if there are zero unknown stops but 5 long idles, only the idle section renders.

If there are no anomalies, a green "no anomalies detected" card is shown instead.

05 Data Pipeline

5.1 — GPS Storage

All GPS data lives in DistLocationLog000:

  • DistributorGUID — links to a distributor
  • [Date] — a UTC timestamp (Syria is UTC+3)
  • Lat — latitude
  • Lon — longitude

5.2 — Customer Visits

DistVi000 (visits) links to DistTr000 (trips) via TripGUID, and to cu000 (customers) via CustomerGUID. Each visit has:

  • StartTime / FinishTime
  • State (0 = open, 2 = completed)
  • No coordinates of its own

5.3 — Coordinate Resolution for Visits

Since stored customer GPS is all placeholders (zeros) in every candidate table (DistCustUpdates000, CustAddress000, DistDeviceCustAddress000), the tracker uses a fallback strategy:

  1. Stored customer GPS — if a non-zero value exists (rare)
  2. Nearest route point within ±15 minutes of the visit's StartTime — this is almost always where the salesman physically was at that moment
  3. NULL — if neither works, the visit appears in the list but has no map marker

This gives us 185 usable customer locations even with zero stored GPS.

5.4 — Distance Calculation

Distance is computed server-side in SQL using the haversine formula with a LAG() window function partitioned by calendar day. This ensures:

  • Overnight jumps between dates are not counted
  • Thinned/decimated points still report accurate total distance
  • A 30-day range returns exact km, not the sum of a decimated subset

5.5 — Anomaly Rules

Unknown stops: Any cluster of GPS points within 150m of each other lasting ≥20 minutes, not overlapping a registered visit (±5 min tolerance), and not within 300m of any known customer location.

Long idles: Same as above, but ≥60 minutes and starting between 08:00 and 18:00 local.

Far starts: First GPS ping of each calendar day located >15 km from the distributor's centroid (average of all their points in the range).

All thresholds are exposed as URL parameters and cached per-distributor-per-date-range for 15 minutes.

5.6 — Territory Coverage Grid

Points are bucketed into cells of 200m × 200m (adjustable via ?cell=). Each cell stores a count. The map renders them on a single canvas with log-scale coloring:

#e0f2fe (few) → #7dd3fc → #3b82f6 → #10b981 → #f59e0b → #ef4444 (many)

Log scale is critical — without it, the occasional hotspot would drown out the everyday usage patterns.

06 Security & Database Access

Read-Only User

CREATE LOGIN alameengeo_reader WITH PASSWORD = '...';
CREATE USER alameengeo_reader FOR LOGIN alameengeo_reader;
ALTER ROLE db_datareader ADD MEMBER alameengeo_reader;
DENY INSERT, UPDATE, DELETE TO alameengeo_reader;
DENY ALTER, CREATE TABLE       TO alameengeo_reader;
DENY EXECUTE                   TO alameengeo_reader;
🔒
Effect: Even if a bug or injection attempt tried to modify data, SQL Server would reject it at the permission layer.

Connection Strategy

app/Database.php tries 4 connection paths in order:

  1. sqlsrv with explicit Driver 18 (Unicode-safe, preferred)
  2. sqlsrv with auto-detected driver
  3. Generic odbc with Driver 18 (fallback — logs a warning)
  4. Generic odbc with Driver 17 (last resort)

Attempt 1 always wins on this environment, which is why Arabic text comes out perfectly.

UTF-8 Encoding

PDO is created with PDO::SQLSRV_ATTR_ENCODING => PDO::SQLSRV_ENCODING_UTF8 on sqlsrv connections. This is what makes Arabic customer names appear correctly in the browser, JSON, and print reports.

07 Frontend Techniques

Coordinate swap switches (SWAP_ROUTE, SWAP_VISIT) — top-level constants. Flipping them swaps lat/lon interpretation if a data source ever reports them inverted.

Native date picker on click — input.showPicker() is called on click event so the calendar opens even if the user clicks the middle of the field.

Anti-flash theme script — runs inline in <head> before CSS loads, reads localStorage.alameen_theme, and sets html[data-theme] synchronously. No theme flicker.

Error boundary — a top-level IIFE installs window.onerror and window.onunhandledrejection handlers. Any uncaught error shows a friendly overlay with Copy / Dismiss / Reload options. Browser extension errors are silently ignored.

Toast notifications — a small queued notification system with 4 types (success, info, warning, error) and a shrinking progress bar. Used for intentional user feedback (load complete, copy link, filters cleared).

Canvas coverage layer — thousands of grid cells are drawn in a single canvas element (not thousands of Leaflet rectangles) for smooth panning and zooming.

URL state — history.replaceState updates the URL silently as filters change. Reloading the page or sharing the URL restores the exact view.

localStorage persistence — filters, toggles, theme, and language persist across sessions.

RTL handling — html[dir="rtl"] flips the entire layout, mirrors the back arrow, and reverses progress bar direction. All Arabic translations use correct Cairo font rendering.

10 What the Application Does NOT Do

To set expectations clearly:

  • No writes to the Alameen database. Zero INSERT, UPDATE, DELETE, ALTER.
  • No scheduled background jobs. Everything runs on-demand from the browser.
  • No authentication layer of its own. It relies on network-level access control (local network + Cloudflare tunnel). If you ever expose it publicly without protection, add Cloudflare Access or basic auth.
  • No real-time updates. The map reflects whatever is in the database at the moment you click Load. Refresh to see newer data.
  • No tax/accounting computations. Financial figures come directly from cu000 and are displayed as stored.

11 Recommended Next Steps

If you ever want to continue:

  1. Enable Apache gzip + browser caching — 2 minutes, biggest perf win available.
  2. Investigate why GPS stopped on 2026-06-06 — the vendor report is drafted, just needs sending.
  3. Backfill customer coordinates into a separate cache table (outside the Alameen DB) — future visits would always show precise markers.
  4. Add a compare.php variant that shows all 10 distributors at once — the code already supports it.
  5. Add a heatmap-by-hour filter — a slider that only shows GPS points for a specific time-of-day range.
  6. Wrap the whole app in a PWA — installable on a phone home screen with offline shell caching.
